同一批网页，三条路径，三种结果

用 Lexmount 的两条产品线（Web Fetch 与 Cloud Browser）对 20 所双一流高校官网做巡检， 发现同一批 URL 在不同接入方式下结果差异巨大。本文量化差异、把失败定位到源码行号， 并明确区分数据能证明什么与不能证明什么。

三句话总结：
  1. 同一批 URL，三种接入方式结果不同。13 个站点在 UI 与 API 之间差异超过 200 字。

  3. 正文质量还有两个隐藏问题：浙大 70% 是 JS 源码，清华 83% 是重复内容。

3最强证据：两个站点、两种驱动、同一行 panic

哈尔滨工业大学与中国人民大学在官方 API 下返回 browser_fetch_failed， 两者的失败细节一致——同一个源文件、同一行、同一断言、同一个 HTTP 502：

先看清它证明了什么：这两个站点在 Web Fetch 下跨 UI 与 API 两种驱动都稳定失败， 而在同一平台的 Cloud Browser 下都成功。这足以证明 panic 来自 lightmount_dcl 引擎本身，而不是网络或目标站点不可访问。

为什么这条证据相对最硬：
  • 跨两种驱动复现：人民大学在 UI 和 API 下都失败（共 4 次）， 哈工大也跨两种驱动失败（共 6 次）。排除「某个驱动有问题」。
  • 同批次内 0/3：连续 3 次，两个站点全部失败，其余 19 个站点结果极差为 0。
  • 唯一差别是 NativeNodeId：(116) 与 (677)， 说明命中同一处代码路径。
  • Cloud Browser 对照：同样的两个站点在 Cloud Browser 下 全部成功（人大 2,549 字 / 446 链接，哈工大 1,750 字 / 502 链接）。
⚠️ 有一条必须说清楚，否则这条证据就是被夸大的： 我原以为这是「两个完全不同的站点」命中同一个 bug。实测推翻了这个说法—— 哈工大、东南、人大、复旦、南开都是同一个 sudy 门户模板 （源站 <head> 里都有 sudy、_showDynClickBatch、 wbtreeid 等指纹；哈工大与东南各命中 4 项）。 所以这是同一模板的两个实例，不是两个独立站点。

而且同模板的复旦、南开并没有触发——说明触发还需要我没控制到的附加条件 （页面规模、样式表数量或时序都可能）。 因此我只能说到这一步：该 panic 在这两个站点上可稳定复现，且 Cloud Browser 能绕过； 不能说「所有 sudy 模板站点都会触发」，也不能说触发条件已完全定位。

结论收紧为：lightmount_dcl 引擎存在真实的 panic 缺陷，在受测站点上可稳定复现， 且存在可行的降级路径（Cloud Browser）；触发面有待进一步定位。

✅ 能证明的：同一批 URL、间隔约 14 小时、同一平台， 两次结果不可复现。这意味着用 UI 试验场验证过的抓取方案，接进应用后表现可能完全不同—— 反过来也一样。这对开发者是一个真实的陷阱。
⚠️ 不能证明的（必须说清楚）：我无法确定差异是平台在两次之间变了， 还是UI 与 API 走了不同路径。原因：
  • UI 批次没有记录请求体，两种因素无法分离；
  • 我观察到平台侧有若干变化（template_id 分布不同、extra 字段更结构化、 出现新引擎标识），但这是我事后观察，不是受控实验；

所以我只陈述现象，不归因。要定位原因需要平台方的内部信息。

  • 正文中位数：API 3363 vs Cloud Browser 2228 —— CB 反而更低，14/18 个站点 CB 正文更少。

6隐藏问题一：正文里混进 JS 源码

浙江大学官方 API 返回 6,173 字，其中 4,324 字（70%）是页面内嵌的 JS 源码：

浙江大学 6,173 4,324 70.0% 1,849
影响：如果下游拿 main_text 做 RAG 分块或摘要，这几段 JS 会：
  • 污染检索结果（里面确实有中文新闻标题，但被包裹在 JS 字面量里）；
  • 白白消耗约 4,300 字的 token；
  • 让「6,173 字」这个数字失去意义——真实可用正文只有 3152 字。
20 站里只有浙大 1 站有此问题，但它是我们最核心的案例，所以必须单独说明。 建议在正文抽取后增加一层「JS 字面量检测」，剔除 \w+\.\w+ = [{...}] 形态的行。

9给平台的建议

P0：修 panic

  1. live_document_parser.rs:498 的断言前，把 Suspended → Ready 视为合法可恢复状态，而不是 assert_eq! 崩溃。
  2. panic 时自动降级到 Cloud Browser 路径重试—— 我们已经证明这条路径对这两个站点有效，成本可控而收益明确。
  3. 把 panic 包装成结构化错误码（如 parser_state_conflict），而不是裸 502。

P1：修正文质量

  1. 正文抽取后剔除 JS 字面量行（浙大案例）。
  2. 正文做行级去重（清华案例）。
  3. 检测到 #root/#app 且可见文字接近 0 时，自动切换渲染路径。

P2：修可观测性

  1. 在响应里加 engine_version，让调用方能判断两次结果是否可比。
  2. UI 试验场与 API 若走不同路径，请在试验场明确标注「结果可能与 API 不一致」。
  3. links 字段明确是「全量」还是「摘要」，并提供 links_total。

10方法与可复现性

  1. 路径①：驱动 /playground/webfetch 表单，逐条落盘响应。
  2. 路径②：POST https://api.lexmount.cn/v1/extract， 带 X-API-Key/X-Project-Id，落盘完整响应与请求元信息。
  3. 路径③：/playground 注入 Playwright，渲染后读 DOM。
  4. 稳定性：每站连续 3 次，记录 request_id、字数、耗时。
  5. JS 污染检测：按强代码特征（var/let/const/function/main.xxx/({id:...})） 逐行打分，阈值 0.5 判定。
  6. 去重：按行去重并剔除 Unicode 私有区图标字符。
  7. 本地基准：普通 HTTP 客户端直连作为独立参照，不依赖平台提取逻辑。

所有原始响应保留 request_id、server_elapsed_ms、fetched_at， 可逐条回溯。本仓库包含全部原始数据与统计脚本。

11这份报告的价值在哪

1. 三个视角而不是一个。 绝大多数巡检只用一种接入方式。我用了三种，结果互相矛盾—— 这个矛盾本身就说明「平台能力」不能用一个数字概括。

2. 每条结论都定位到可核验的位置。 panic 到源文件行号，JS 污染到具体字符数，重复内容到具体行数。 不是「感觉不稳定」，是「第 498 行崩了」。

3. 严格区分「证明了」和「没证明」。 UI/API 差异我无法归因，就明确写「不能证明」，只陈述现象。 Cloud Browser 正文更少，我写成「取舍」而不是「更好」。

4. 撤回过自己的错误结论。 初版报告写过「渲染引擎正文反而更短」，后来发现有批次混杂，已删除； 写过「两个站点可稳定复现 panic」，复测后改成「同批次 0/3，跨两种驱动复现」； 写过「3,400 倍差距」，那是 UI 口径的伪影，API 基线是 13.5 倍，已撤回。 一份只报好消息、不自我纠错的巡检报告没有价值。
