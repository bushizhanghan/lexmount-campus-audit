同一批网页，三条路径，三种结果

我用 Lexmount 的两条产品线（Web Fetch 与 Cloud Browser）抓取 20 所双一流高校官网， 发现同一批 URL 在不同调用路径下结果差异巨大：有的站点在表单里只有 4 个字， 走官方 API 变成 6,000 多字，而 Cloud Browser 全部成功。 本文量化这种差异，并把每一类失败定位到具体代码位置。

3方法：为什么会有三条路径

这不是刻意构造的三组实验，而是我实际用过的三种接入方式：

  1. UI 表单（路径①）：在 /playground/webfetch 页面填 URL、点「运行请求」。 这是官网推荐的免登录体验方式，也是最容易被新手采用的方式。
  2. 官方 API（路径②）：POST https://api.lexmount.cn/v1/extract， 带 X-API-Key 与 X-Project-Id 请求头。 这是文档里的正式接入方式，也是应用实际会用的方式。
  3. Cloud Browser（路径③）：在 /playground 注入 Playwright 脚本， 用云端真实浏览器渲染页面后读取 DOM。
为什么这件事值得做：如果我只用路径①，会得出「2 个站点空正文 + 2 个站点 panic」； 只用路径②，会得出「0 个空正文 + 2 个 panic，但是另外两个站点」； 只用路径③，会得出「全部正常」。 三条结论互相矛盾，而它们都来自同一个平台。

但 Cloud Browser 也不是万能的。它的正文字数普遍低于 Web Fetch—— 南京大学例外（11,167 字），但华中科技大学只有 381 字、北京师范大学 354 字。 原因是我们直接读 document.body.innerText，没有做正文抽取， 所以把导航、页脚等噪音也算进去或屏掉了。两条路径的取长补短才是正解。

8另一个被忽略的问题：正文重复

清华大学的 main_text 有 9,794 字，但按行去重后只剩 1,630 字—— 83.4% 是重复内容。同一行文字在响应里重复了多次。

影响：如果下游拿 main_text 做 RAG 分块或摘要，清华这一站会白白消耗 8,000 多字的 token，而且重复内容会污染检索结果。 去重后 20 站中位数从 3398 降到 3090 字。

这类问题在模板循环渲染的页面上很容易出现，而平台的提取逻辑没有做去重。 建议在 main_text 输出前加一层行级去重，或提供 main_text_deduped 字段。

10给平台的具体建议

针对 panic（最高优先级）

  1. 在 live_document_parser.rs:498 的断言前，把 Suspended → Ready 视为合法可恢复状态，而不是直接 assert_eq! 崩溃。
  2. 把引擎 panic 捕获为结构化错误码（如 parser_state_conflict）， 并自动降级重试——既然 Cloud Browser 能读，说明降级路径是可行的。

针对路径不一致

  1. 排查 UI 试验场与 API 走的是否为同一套引擎/队列/缓存；如果不同， 在试验场明确标注「结果仅供参考，可能与 API 不一致」。
  2. 给响应加 engine_version 字段，让调用方能判断结果的可比性。

针对正文质量

  1. main_text 输出前做行级去重，或提供 main_text_deduped。
  2. 检测到 #root/#app 且可见文字接近 0 时，自动切换渲染路径。
  3. 正文为空但存在 meta description 时返回 fallback_text 降级字段。

针对 links

  1. 明确 links 是「全量」还是「摘要」，在文档写明上限。
  2. 若保留摘要语义，增加 links_truncated 与 links_total。

11方法与可复现性

  1. 路径①：驱动 /playground/webfetch 页面表单，逐条落盘响应。
  2. 路径②：POST https://api.lexmount.cn/v1/extract， 带 X-API-Key/X-Project-Id，落盘完整响应与请求元信息。
  3. 路径③：在 /playground 注入 Playwright 脚本， 渲染后读 document.body.innerText 与 a[href] 数量，原始输出落盘。
  4. 稳定性：每站连续 3 次，记录 request_id、字数、耗时。
  5. 去重分析：按行去重并剔除 Unicode 私有区图标字符后重新统计。
  6. 本地基准：用普通 HTTP 客户端直连作为独立参照，不依赖平台提取逻辑。

所有原始响应都保留 request_id、server_elapsed_ms、 fetched_at，可逐条回溯。本项目同时开源了 Cloud Browser 实验脚本与全部统计代码。

12我认为最有价值的三点

1. 三个视角，而不是一个。 绝大多数巡检报告只用一个接入方式。我用了三个，结果互相矛盾—— 而这个矛盾本身就比任何单条结论更有价值。它说明「平台能力」不能用一个数字概括。

2. 每条结论都有可核验的定位。 panic 定位到源文件行号，正文重复有去重前后的对比数字， 路径差异有完整的逐站对照表。不是「感觉不稳定」，是「第 498 行崩了」。

3. 我也报告了对自己不利的结果。 UI 与 API 的差异无法完全解释，我照原样写出来并标明「未经证实」； 正文重复问题是我自己数据的缺陷，我把它算进中位数修正。 一份只报好消息的巡检报告没有价值。
