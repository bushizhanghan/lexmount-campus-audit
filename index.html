3问题一：拿到 HTML，却提取不出正文

现象：浙江大学返回 HTTP 200、title 正确，但 main_text 仅 4 个字符， links 为 0。平台 debug 写着 content_length: 4、selector: body(fallback)。

对照实验：extract 与 dom/dump 同时跑

站点dump HTML 大小去标签后可见文字 extract 正文字数SPA 标记判定
北京大学 118,214 6,507 5925 否 内容完整
清华大学 86,348 3,654 9794 否 内容完整
浙江大学 88,480 4 4 是 内容缺失

结论很直接：浙大 dump 回来的 HTML 有 88,480 字符，去标签后只剩 4 个字， 和 extract 完全一致——HTML 里本来就没有正文内容，不是提取算法的问题。

本地直连复核同一页面：

  • <body> 有 87,546 字符，去掉 <script>/<style> 后可见文字为 0
  • 页面含 id="root"，34 个 <script>，是 React 客户端渲染的 SPA
  • 但 <meta name="description"> 完整——信息存在，只是不在 DOM 文本里
根因：目标是 CSR 的 SPA，服务端返回空壳 HTML。当前 lightmount_lite 走 safe_http.get 快速路径，不执行页面 JS，因此拿不到正文。

建议：

  1. extract 增加 render: true，允许调用方主动要求走浏览器渲染路径；
  2. 检测到 body 可见文字接近 0 且存在 #root/#app 时自动降级重试；
  3. 正文为空但存在 meta description 时返回降级字段（如 fallback_text）。

补充：这个现象不能全算平台的问题——SPA 对任何非渲染型工具都一样不友好。 但平台有能力渲染，缺的只是「发现空正文后自动切换」的策略。

4问题二：引擎内部 panic

现象：东南大学、哈尔滨工业大学直接失败，返回 error.code = browser_fetch_failed，stage = fetch。 不是超时，不是目标站点拒绝，而是渲染引擎在 Rust 层 panic。

为什么这个发现值得重视

  • 可稳定复现：两个完全不同的站点，命中同一源文件同一行 live_document_parser.rs:498。
  • 不是网络问题：失败耗时 3–4.5 秒，远低于超时阈值，是解析阶段主动 abort。
  • 与页面结构相关：断言里的 ParserClassicStylesheets { script: NativeNodeId(...) } 指向「解析器在等待样式表加载时被挂起，之后又被要求进入泵会话」的状态机冲突。
  • 影响面可能更大：任何在 <head> 同步插入 <link rel=stylesheet> 且伴随脚本执行的页面都可能触发。

复现线索：

  1. POST /v1/extract，body {"extract":{"url":"https://www.seu.edu.cn"}}
  2. 期望 200 + 正文；实际 panic
  3. 建议把 Suspended → Ready 视为合法可恢复状态，而非直接 assert_eq!
  4. 把引擎 panic 捕获为结构化错误码（如 parser_state_conflict），而非整站失败

方法论修正（重要）：我最初的比对脚本直接把两边的 href 字符串对比， 得出「平台返回数 > 本地 <a> 数」的矛盾结论（北师大、中科大）。 深挖后发现原因是平台把相对 URL 规范化成了绝对 URL： 本地 xxgk/gljg.htm → 平台 https://www.ustc.edu.cn/xxgk/gljg.htm。 修正口径后结论才稳定。这也是本次分析里唯一一处「差点报错」的地方， 记录下来是因为它说明验证抓取工具的返回，必须先用独立基准对齐口径。

影响：任何依赖 links 做站点地图、入口发现、批量巡检的任务， 都会静默漏掉三到八成的链接，而且调用方无法知道自己漏了多少。

建议：

  1. 明确 links 是否设计为「全量」还是「摘要」，并在文档中说明上限；
  2. 若保留摘要语义，增加 links_truncated: true 与 links_total 字段；
  3. 提供分页或 limit 参数，让调用方能取到全集。

6问题四：正文被选择性丢弃

现象：上海交通大学平台返回 1,865 字，本地裸抓可见文字 2,840 字， 平台少了 34%。做句子级比对后发现：裸抓独有的句子 19 条，平台独有的只有 3 条。

被平台丢弃的是这些内容：

  • 徐汇校区『中院』的建筑介绍整段（"中院采用的是英国样式主义风格，设计师福开森的说法是…"）
  • 闵行校区『李政道图书馆』的介绍（"实体图书馆总建筑面积 6,500 平方米…"）
  • "李政道图书馆开创性地实现了包括图书馆、档案馆、博物馆、科技馆和艺术馆在内的五馆合一"
  • 多段校园新闻正文（"其外立面没有非常繁复的装饰和复杂的柱头柱式…"）

而平台保留的是标题、列表项和快速入口。

根因判断：平台把页面里的长段落正文当成了导航噪音过滤掉， 只保留了短标题和列表。这不是截断，是选择性丢失—— 对一个想读「学校介绍」的 Agent 来说，恰好丢掉了最有价值的部分。

对比之下，同济大学反而是 1.30x（平台比裸抓长），说明这个过滤行为在不同模板上 表现不一致，进一步印证规则不透明。

9extra 字段的 schema 不统一

同一个 extra 字段，在 18 个成功响应里出现三种互不兼容的形态：
形态站点数内容
dom_summary 家族15 dom_summary + images_detail + metadata + site_links
仅 metadata2 只有 metadata（浙大、华南理工——恰好都是空正文站点）
无 extra1 整个字段缺失（清华大学）

更细一层，dom_summary 内部的键也不稳定：

  • lists 出现在 15/18 个站点，paragraphs 14/18，headings 13/18
  • forms 只有 7/18，tables 只有 3/18
  • 清华的 extra 整个为空，但它的正文有 9,794 字——结构化数据缺失与内容量无关

影响：下游按固定 schema 解析的代码会直接崩溃或静默跳过。 而 site_links 与顶层 links 在所有站点上内容完全相同 （缺失率 0%），属于冗余字段。

10横向观察

meta description 可用率极低

18 个成功站点里，只有 3/18 个有可用的 <meta name="description">（≥20 字）：复旦、中山、浙大。 其余 15 个站点这个字段完全缺失——而它本该是 AI 最省 token 的摘要来源。

正文字数差异极大

20 个站点从 4 到 13,751 字，中位 3398 字。 最高（复旦）与最低（浙大）相差 3,400 倍。同样的调用方式，产出质量完全不可预期。

语言标记不稳定

language 字段出现 4 种取值：空（9 次）、zh-cn（6 次）、 en（2 次）、zh-hans（1 次）。 中文站点有近一半没返回中文标记，下游做多语言分流时不可靠。

11方法与可复现性

  1. 抓取：POST /v1/extract，目标为各校官网首页，逐条落盘原始响应 JSON。
  2. 对照：3 个代表站点追加 POST /v1/dom/dump，交叉验证正文来源。
  3. 本地基准：12 个站点用普通 HTTP 客户端直连，规范化后与平台返回逐条比对 ——不依赖平台的提取逻辑，避免自己验证自己。
  4. 原始数据：每个站点保留 request_id、server_elapsed_ms、 debug.attempts，可逐条回溯。
  5. 脚本：drive.mjs 批量执行；analyze.py 统计； verify_links_final.py / value_added.py 做本地对照； render_report_v2.py 生成本报告。

12结论与价值

这次巡检的价值不在「抓了 20 个网站」，而在于把失败分了类，并且每类都能定位到具体原因：

  • 目标站点的问题（SPA 不渲染就没内容）—— 平台可做自动降级缓解；
  • 平台自身的问题（解析器 panic、链接不全、正文被过滤）—— 属于必须修的缺陷。

如果不做这个区分，看到「4 个站点失败」很容易笼统归结为「抓取不稳定」， 从而错过一个具体的、可定位的引擎缺陷。它把一个模糊的产品感受， 变成了可以贴到 issue 里的堆栈行号。

更重要的是第 7 章的负结果：云平台相对裸抓并没有抓到更多内容， 它的价值在结构化输出和省掉的解析工作。如实记录这一点， 比把它包装成「抓取能力强多少倍」更有用——因为只有知道短板在哪，才知道该怎么用它。
